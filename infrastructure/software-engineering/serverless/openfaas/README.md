# OpenFaaS

<https://github.com/openfaas/faas>
<https://github.com/openfaas/faas-netes>

---

## The problem it solves

The **simplest** function platform that works on Kubernetes, and the one that hides the least.

Every OpenFaaS function is an ordinary container that speaks HTTP. A watchdog process inside the
image handles the request and hands it to your handler, so there is no special runtime to
understand: if you can build an image, you can run a function. The gateway in front provides the
URL, the invocation metrics and the scaling signal.

Two repositories, two layers, which is what the original note records:

| Repository | Layer |
|---|---|
| `openfaas/faas` | the gateway, the watchdog, the function model itself |
| `openfaas/faas-netes` | the Kubernetes provider and the Helm chart — how that model is realised as Deployments |

The workflow is CLI-first: `faas-cli new`, `faas-cli up`, and a `stack.yaml` describing the
functions. That makes it fast to get started and slightly awkward to keep in a GitOps repository,
where you would rather commit `Function` resources than run a CLI.

## When to use it

- you want a function platform running **this afternoon**, with the least conceptual overhead
- functions are plain containers by design — no vendored runtime, no injection, no build system to
  operate
- the team is comfortable with a CLI-driven workflow

## When not to use it

- cold start is the constraint — OpenFaaS starts a pod per function, so this is the plain version
  of the problem; [Fission](../fission/README.md)'s pre-warmed pool is the answer to it
- **the edition boundary matters to you.** The project is split into a community edition and
  commercial editions, and capabilities move between them over time. Check that what you are
  relying on is in the edition you intend to run *before* building on it — this is the single most
  common surprise with OpenFaaS
- you want everything declared as CRDs and reconciled by Flux, with no CLI in the loop

## Notes

**What is deployed here:** chart `openfaas` 14.2.90 from `https://openfaas.github.io/faas-netes/`,
in the `openfaas` namespace.

**The values are minimal and deliberate:**

```yaml
functionNamespace: openfaas
# port-forward gateway, login in secret basic-auth
#dashboard:
#  enabled: true
#  publicURL: "localhost"
```

Three things are recorded in those five lines, and they are worth spelling out.

`functionNamespace: openfaas` puts deployed functions in the **same namespace as the control
plane**. The chart's usual pattern is a separate `openfaas-fn` namespace, and separating them is
what lets you apply different quotas, network policies and RBAC to untrusted function workloads
than to the gateway. Collapsing them into one namespace is fine for evaluation and is the thing to
revisit before anything real runs on it.

The comment `port-forward gateway, login in secret basic-auth` is the access note: there is **no
ingress** configured, so the gateway is reached with `kubectl port-forward`, and the credentials
are generated by the chart into a secret named `basic-auth` rather than being set here. That is
the correct evaluation posture — nothing is exposed, and no password is committed.

The **dashboard is commented out, not disabled by accident.** It is left in place with a
`publicURL` of `localhost` as a note on how it would be enabled: the dashboard needs to know the
URL it is served from, and with port-forwarding that URL is `localhost`. Enabling it means
deciding on real ingress first.
