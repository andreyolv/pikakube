# Locust

<https://github.com/locustio/locust>

---

## The problem it solves

**Load tests written as ordinary Python, with the whole Python ecosystem available.**

A Locust scenario is a class with methods; the load is generated by running that code. That means
anything importable is usable inside the test: the service's real client library, an SDK, `pandas`
to build realistic payloads, a database connection to seed state, a signing library for
authentication.

That is the axis where it beats [k6](../k6/README.md) outright. k6 scripts run on a Go engine that
executes JavaScript — there is no package manager and no library ecosystem, so anything beyond
HTTP-shaped work needs a compiled extension. Locust just imports it.

It is also **distributed out of the box** — one master, many workers, no operator required — and it
ships a **live web UI** that shows requests per second, response times and failures while the test
is running, with controls to change the user count mid-run. For exploratory work, watching the
system respond as you turn the load up is genuinely more useful than reading a summary afterwards.

## When to use it

- **the load generation itself needs real code** — an SDK, a protocol library, a non-HTTP client
- exploratory testing where a **live UI and interactive control** of the user count matter
- a Python team, testing a Python service, reusing its own client
- complex user behaviour: weighted task selection, stateful sessions, conditional flows
- distributed runs without introducing a Kubernetes operator

## When not to use it

- **very high concurrency on limited hardware** — each simulated user costs more than in
  [k6](../k6/README.md); the same load needs more workers
- **a Kubernetes-native, GitOps-managed load test** — k6 has the
  [k6-operator](../k6/README.md) and a `TestRun` CRD; Locust would need something built
- when the team does not write Python
- as a functional API test — that is [`api/`](../../api/README.md)
- without an SLO to compare the result against —
  [`service-level/`](../../../../site-reliability-engineering/service-level/README.md)

## Notes

The recorded note is a single link — <https://github.com/locustio/locust> — the community project,
with no vendor behind it, in contrast to [k6](../k6/README.md) being Grafana's. That difference shows
up in the tooling around each: k6 has an operator and a metrics integration into a stack this
platform already runs; Locust has a library and a web UI, and how it is deployed is left to you.

**Nothing is deployed for Locust in this repository.** It stays documented because the reason to
choose it does not overlap with k6's:

| | k6 | Locust |
|---|---|---|
| Chosen for | thresholds, the operator, low footprint, Grafana integration | **Python, and every library in it** |
| Deployed here | **yes** — operator 3.10.1 | no |

If Locust is needed, the shape it takes on Kubernetes is a `Deployment` for the master and a scaled
`Deployment` for the workers, with the locustfile mounted from a `ConfigMap` — the same pattern the
[k6 `TestRun`](../k6/README.md) uses, assembled by hand instead of by an operator.

One caveat that applies whichever tool is used and bites harder here, because Python workers cost
more per user: **watch the workers' own CPU during the run.** A saturated generator reports its own
queueing as the service's latency, and that is the most common way to produce a load test result
that is simply wrong.
