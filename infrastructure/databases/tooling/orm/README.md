# ORMs

How application code talks to the database — and the queries it emits when nobody is looking.

Tools covered: [SQLAlchemy](https://github.com/sqlalchemy/sqlalchemy) ·
[SQLModel](https://github.com/fastapi/sqlmodel) ·
[Peewee](https://github.com/coleifer/peewee)

---

## Why this is in a platform repository

An ORM is an application concern, and it becomes a platform concern for one reason: **the
platform inherits the queries it generates.**

The connection between this folder and the rest of [`tooling/`](../README.md) is direct:

| ORM behaviour | What it becomes |
|---|---|
| **N+1 queries** | thousands of round trips, and a database that looks busy doing nothing |
| Generous default pool sizes | connection exhaustion — see [`pooler/`](../pooler/README.md) |
| Lazy loading in a loop | the same, from a different direction |
| `SELECT *` by default | more I/O than the query needs, on every call |
| Migrations from model changes | [`migration/`](../migration/README.md), and the rename trap |
| Session-scoped state | breaks under transaction pooling |

The last row is the one that connects most sharply. An ORM using prepared statements or
session-level `SET` will misbehave behind a pooler in transaction mode, intermittently, under
load — and the symptom appears nowhere near the cause. See
[`pooler/`](../pooler/README.md#3-what-breaks-in-transaction-mode).

## The three here

| Tool | Position |
|---|---|
| **SQLAlchemy** | the Python default — a full ORM *and* a SQL toolkit, and the toolkit half is underrated |
| **SQLModel** | SQLAlchemy plus Pydantic, from FastAPI's author — models that are both ORM entities and validated API schemas |
| **Peewee** | small, simple, and enough for scripts and small services |

**SQLAlchemy's Core is worth knowing separately from its ORM.** It builds SQL programmatically
without mapping objects — which is frequently what data work actually needs, and it avoids the
identity map and lazy-loading behaviour that cause the problems above.

**SQLModel** is the sensible default in a FastAPI service, because the alternative is defining
the same fields twice — once as a Pydantic schema and once as an ORM model — and letting them
drift.

**Peewee** is the right size for a utility, a maintenance job, or a small internal tool where
SQLAlchemy is more machinery than the problem.

## The N+1 problem

The single most common way an ORM causes a production incident, and it is invisible in the code:

```python
for order in session.query(Order).all():   # 1 query
    print(order.customer.name)              # 1 query PER ORDER
```

A hundred orders is 101 queries. The code reads as a loop over objects; the database sees a flood
of tiny round trips, each with its own latency.

The fix is one line — eager loading, a join, or a batched fetch — and finding it requires
**seeing the emitted SQL**. Which is the whole discipline:

| Practice | Why |
|---|---|
| **Log the SQL in development** | `echo=True` in SQLAlchemy; the number of queries is immediately obvious |
| Assert query counts in tests | the only way N+1 regressions are caught before production |
| **Review generated SQL for hot paths** | not every query, the ones that run constantly |
| Use [pghero](../monitoring/pghero/README.md) | queries ranked by total time, which is where these surface |
| Drop to raw SQL where it matters | an ORM is not an obligation |

## Anti-patterns

| Anti-pattern | Why it is bad | What to do instead |
|---|---|---|
| Never looking at the emitted SQL | N+1 and full scans ship unnoticed | log it in development |
| Lazy loading inside a loop | the N+1 problem, in its usual disguise | eager load, or join |
| The ORM used for analytical queries | object mapping over a million rows is pure overhead | raw SQL, or the warehouse |
| Default pool size × many replicas | connection exhaustion — see [`pooler/`](../pooler/README.md) | size the pool deliberately |
| Prepared statements behind a transaction pooler | intermittent failures under load only | disable them, or use a pooler that tracks them |
| Autogenerated migrations applied unread | a renamed column becomes drop-and-add, losing the data | read every generated migration |
| The ORM as the only database interface | some things are far clearer in SQL | mix deliberately |
| Models as API schemas without thought | internal storage decisions leak into the contract | separate them, or use SQLModel knowingly |

## How this applies to pikakube

Mapped rather than deployed, because these are libraries rather than infrastructure — but the
platform's Python components use them, and
[Airflow](../../../data-engineering/orchestration/airflow/README.md) is built on SQLAlchemy.

The connections that matter here:

- **[`pooler/`](../pooler/README.md)** — the ORM's pool size multiplied by the replica count is
  the number that exhausts PostgreSQL. This is the named gap for the platform, and the ORM is the
  other half of it
- **[`migration/`](../migration/README.md)** — [Alembic](../migration/alembic/README.md) is
  SQLAlchemy's migration tool, and its autogenerate caveats apply
- **[`monitoring/`](../monitoring/README.md)** — [pghero](../monitoring/pghero/README.md) is where
  ORM-generated problems become visible, ranked by total time

The practical takeaway: the ORM is chosen by whoever writes the service, and the platform is what
absorbs the consequences. Making the emitted SQL visible in development is the cheapest available
intervention.
