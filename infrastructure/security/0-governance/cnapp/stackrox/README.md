# StackRox

<https://github.com/stackrox/stackrox>
<https://github.com/stackrox/helm-charts>

---

## The problem it solves

A cluster accumulates security tools that each see one thing: a scanner that knows about CVEs,
a policy engine that knows about manifests, a sensor that knows about syscalls. None of them
knows what the others know, and none of them can say which finding matters.

StackRox is a Kubernetes-first security platform that puts them behind one data model. It is
Red Hat's, open-sourced in 2021 as the upstream of Red Hat Advanced Cluster Security, and its
scope covers most of what the numbered rings in [`security/`](../../../README.md) split apart:

| Capability | What it does |
|---|---|
| **Admission control** | blocks deployments that violate policy, at the API server |
| Image scanning | vulnerabilities in images and their components |
| Configuration policy | privileged pods, host mounts, missing limits, exposed secrets |
| Runtime detection | process and network behaviour inside containers |
| **Network policy generation** | observes actual traffic and produces the NetworkPolicies that would permit it |
| Compliance | CIS Kubernetes and Docker benchmarks, with reporting |
| Risk ranking | combines configuration, vulnerability and runtime signals into a per-deployment score |

Two of those are the reasons to prefer it over assembling the pieces. **Network policy
generation** solves the practical problem that stops most teams from adopting NetworkPolicies
at all — nobody knows what traffic is actually required, so nobody dares default-deny.
Observing real traffic and emitting the policy turns a research project into a review. And
**risk ranking** is the correlation argument from
[`../README.md`](../README.md#2-the-real-argument-is-correlation) made concrete: a ranked list
of deployments rather than a flat list of findings.

## When to use it

- **Kubernetes is the estate**, and enforcement inside it is the priority. StackRox is stronger
  here than at multi-cloud posture
- you want admission control and runtime detection and scanning from one system, with findings
  that reference each other
- **NetworkPolicy adoption has stalled** because nobody can enumerate required traffic — the
  generation feature is worth the deployment on its own
- OpenShift is in the picture; this is the upstream of the product Red Hat ships there, so the
  path is well trodden
- CIS Kubernetes benchmark reporting is a recurring requirement and you would rather not pipe
  `kube-bench` output into a spreadsheet by hand

## When not to use it

- a small estate. Central services plus a per-cluster sensor is a substantial deployment, and
  the correlation payoff needs volume — see
  [`../README.md`](../README.md#8-how-this-applies-to-pikakube)
- **cloud posture is the actual gap**. StackRox is Kubernetes-first; CSPM breadth across cloud
  accounts is not its strength, and `1-cloud/scan/` tools cover it better
- when the individual controls are not understood yet. Its findings need tuning, and tuning
  requires knowing what a privileged pod or a missing seccomp profile actually implies
- when best-of-breed components already work and nobody is complaining about console count —
  Trivy, Kyverno and Falco each beat StackRox's equivalent in isolation
- if a privileged, cluster-wide component with an admission webhook is not acceptable. Its
  failure mode is a security tool that can block every deployment

## Notes

Original references recorded for this tool:

> <https://github.com/stackrox/stackrox>
> <https://github.com/stackrox/helm-charts>

Both are open source, and that is genuinely unusual for this category — the CNAPP space is
almost entirely commercial, and StackRox is the one whose full platform can be run without a
licence. It is worth knowing that the open-source project and Red Hat Advanced Cluster Security
are the same code with different support and packaging, so what is learned here transfers
directly to the commercial product.

**The chart is unusual and worth recording.** The `HelmRepository` staged in this repository
points at `https://raw.githubusercontent.com/stackrox/helm-charts/main/opensource/` — a raw
GitHub path, not a conventional chart repository host. That works, and it means chart
availability depends on a branch in a Git repository rather than on a repository index, which
is more fragile than usual. The chart staged here is `stackrox-central-services` at version
`400.5.5`.

**It is two installs, not one.** `stackrox-central-services` is the central component — the
UI, the API, the scanner and the database. A **separate** `stackrox-secured-cluster-services`
chart installs the sensor, admission controller and collector into each cluster being
protected, and it requires an init bundle generated by central. Only the central half is staged
here, so as configured this would deploy a console watching nothing. That is the first thing to
fix if it is ever brought up.

**Turn admission control on last.** The admission controller is the feature with real teeth
and it is also the one that can stop every deployment in the cluster. The sequence that works
is: deploy, run policies in inform-only mode, look at what would have been blocked, then
enforce policy by policy. Enabling enforcement with the default policy set on an existing
cluster reliably blocks something important.
